# Issue Draft

粗いアイデアを考え抜いて GitHub issue として起票する。

## 手順

1. **仕様を先に確認する。** 対象ページのディレクトリにある `page.spec.md`（なければ関連コンポーネントの `ComponentName.spec.md`）を必ず読む。意図した挙動をバグとして issue 化することを防ぐ（プロジェクトルール）。
2. **コードを調査する。** 関連するコード領域（コンポーネント、状態管理、`lib/server/` の fetch 関数、類似の既存機能）を読んでから書き始める。issue は今のコードが実際にどう動いているかを反映していなければならない。
3. **重複を確認する。** `gh issue list --search "..."` で既存 issue を検索し、カバーする open issue があれば新規作成せずリンク・更新を提案する。
4. **下書きを作る**（日本語で）:
   - 問題提起・動機 — 今なにが不便か、なにが欠けているか
   - 現在の挙動（有用な箇所には `file:line` アンカーを付ける）
   - 設計の選択肢を 2〜4 案、トレードオフ付きで列挙し、推奨案を明示する
5. **決めるべきことリスト** — 実装前にユーザーが決断すべき事項を明示的なチェックリストにする。起票**前に**ユーザーに提示し、「で、何を決めれば良い？」を先回りする。
6. **起票**: `gh issue create --title "..." --body "..."`。ラベルは `gh label list` で既存の運用を確認して付ける。ただし「AI調査結果承認済・修正待ち」等の AI 修正フロー用ラベルは承認を意味するため、ユーザーの確認なしに付けない。URL を返す。
7. **停止する。** 実装を始めない — それは別のリクエストである（issue → 修正フローはルーティンまたは明示的な依頼で動く）。

## 補足

- 1 つの依頼に複数のアイデアが混ざっている場合は issue の分割を提案し、分け方をユーザーに確認してから起票する。
