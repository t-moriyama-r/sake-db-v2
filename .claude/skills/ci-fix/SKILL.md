# CI Fix

赤くなった GitHub Actions の実行を診断・修正し、緑に戻るまで見届ける。

※ このリポジトリに GitHub Actions が未導入の間は対象がない。Amplify Hosting のビルド失敗の場合、ログは AWS コンソール側にあるため、ユーザーにログの貼り付けを依頼する。

## 入力

Actions 実行 URL、PR の URL / 番号、または引数なし。引数がなければ現在のブランチから推測する: ブランチの PR に対する `gh pr checks`、または `gh run list --branch <branch> --limit 5`。

## 手順

1. **失敗箇所を特定する**
   - 実行 URL → `gh run view <id> --log-failed`
   - PR → `gh pr checks <n>` で失敗しているチェックを見つけ、その実行 ID を取る
2. **最初の本当のエラーを見つける。** CI のログは連鎖するため、最後のエラーはたいてい症状にすぎない。失敗したステップの中で最も早い失敗を探す。
3. **失敗を分類する**:
   - lint / 型チェック / ビルド → ローカルで再現する（`npm run lint`、`npx tsc --noEmit`、`npm run build`）
   - 依存関係のズレ（lockfile、Node バージョン）→ CI 環境とローカルを比較する
   - デプロイ・権限系 → IAM / 設定の問題であってコードではない。ソースを触る前にロールと設定を調べる
   - flaky / インフラ系（ネットワークタイムアウト、ランナーイメージ）→ まず再実行: `gh run rerun <id> --failed`
4. **修正の前に根本原因を特定する**（`docs/debugging-methodology.md` 参照）。リグレッションなら `git log` や直近のマージから原因のコミットを探す。
5. ビルド成果物を直接修正しない — ソースを直して再ビルドする。
6. PR ブランチ上で修正する（develop / main 上では作業しない）。ローカルの検証ゲートをすべて通す: `npx tsc --noEmit && npm run lint && npm run build`。
7. `fix: <内容>` でコミットし、プッシュする。
8. **再実行を見届ける**（`gh run watch <id>` または `gh pr checks <n> --watch`）。まだ赤なら新しいログで手順 1 からやり直す。

## 補足

- 複数のチェックが失敗している場合: ローカルで検証できるものは 1 コミットにまとめて修正し、再確認する。
- 根本原因が別リポジトリ（共有 Action、公開パッケージ）にある場合は、症状に絆創膏を貼らずその旨を報告する。
