# Test Writing

`docs/testing.md` の規約に従って Vitest のユニットテストを書く。着手前に必ず同ドキュメントを読むこと。

## 手順

1. **対象を分析する。** テストしたい「ルール」（判断・変換・バリデーション）がどこにあるかを特定する。ルールが I/O（Amplify クライアント、fetch、ファイル）と絡み合って埋もれている場合は、まず純粋関数として独立ファイルに抽出する — アプリを起動しないと到達できないルールはテストできない。
2. **仕様を確認する。** 対象に関連する `.spec.md`（`page.spec.md` / `ComponentName.spec.md`）があれば読む。テストは記録された意図した挙動を反映しなければならない。
3. **テストファイルを作る。** 対象と同じディレクトリに `<対象ファイル名>.test.ts(x)`。`import { describe, it, expect } from 'vitest'` を明示する（グローバル注入は使わない）。
4. **パターンを網羅する。** `docs/testing.md` のチェックリスト（ハッピーパス／エッジ／境界値／空／null・undefined／不正入力／エラー／ネガティブ）から対象に意味のあるものを選んで書く。テスト名は日本語で挙動を記述する。
5. **モックの方針**: モジュールモック（`vi.mock`）より、パラメータで渡すフェイク・スタブを優先する。外部 API（aws-amplify 等）は必ずモックし、AWS 認証情報なしで実行できるようにする。async な Server Component は対象にしない — ロジックを抽出してテストする。
6. **ミューテーション確認。** 書いたテストが「対象コードが壊れたときに落ちる」ことを確認する: 対象の条件を一時的に反転させ、テストが赤くなるのを見届けてから戻す。壊れたコードでも通るテストは別の何かをテストしている。
7. **検証する**: `npm run test` が全件緑、`npx tsc --noEmit` と `npm run lint` も通ること。

## 補足

- 既存コードのバグをテスト作成中に発見した場合、勝手に修正せずユーザーに報告する（テストは現在の意図した挙動を固定するもの）。
- 意図的な非対称性・既知の制限をテストで固定する場合は、理由をコメントに書く。
