# テスト — パターン・テスタブル設計・プロジェクト規約

テストを書くとき・リファクタリングするときに読むこと。

## テスト環境

- テストランナーは **Vitest**（Next.js 公式ガイド準拠: Vitest + React Testing Library + jsdom）
- 実行コマンド: `npm run test`（一括実行）/ `npm run test:watch`（監視モード)
- 設定は `vitest.config.mts`。`vite-tsconfig-paths` により `@/` エイリアスがそのまま使える

## テストファイルの配置

- テスト対象と**同じディレクトリ**に `<対象ファイル名>.test.ts(x)` を置く（コロケーション。`.spec.md` と同じ思想）
  - 例: `lib/liquor/rating.ts` → `lib/liquor/rating.test.ts`
  - 例: `components/ui/StarRating/StarRating.tsx` → `components/ui/StarRating/StarRating.test.tsx`
- `.spec.md` は「意図した挙動の記録」、`.test.ts` は「実行可能な検証」。仕様が `.spec.md` にあるならテストはそれを反映すること
- vitest のグローバル注入は使わない。`import { describe, it, expect } from 'vitest'` を明示する

## このプロジェクト特有の制約

- **外部 API は必ずモックする。** テストは AWS 認証情報・Sandbox なしで実行できなければならない。`aws-amplify` / `lib/amplify-client.ts` / `lib/server/client.ts` に触れるコードは、クライアントを注入可能にするか `vi.mock` でモックする
- **async な Server Component は Vitest でユニットテストできない**（Next.js 公式ガイドの注意事項）。ページやサーバーコンポーネントの検証はロジックを純粋関数として抽出してテストする
- `sake-db/`（旧版）配下にはテストを書かない（編集禁止領域）

## ユニットテストのパターンチェックリスト

ユニットテストでは以下のパターンを網羅する:

- ハッピーパス（想定どおりの通常入力）
- エッジケース（珍しいが正当な入力）
- コーナーケース（複数のエッジ条件の組み合わせ）
- 境界値（最小値・最大値・off-by-one）
- 空のケース（空文字列・空配列・空オブジェクト）
- null / undefined のケース
- 不正な入力（型違い・壊れたデータ）
- エラーケース（想定される失敗・例外）
- ネガティブケース（起きては**ならない**こと）
- リグレッションテスト（過去に見つかったバグ）

## テスタブル設計

- **判断と I/O を分離する。** ルール（フィルタ・順序付け・上限・バリデーション・整形）は**独立したファイルの純粋関数**に置き、呼び出し側がファイル読み書き・ネットワーク・Amplify クライアントを持つ。アプリを起動しないと到達できないルールはテストされない。
- 純粋にできない境界では**依存性注入**を使う — `now()`、クライアント、ファイルパスなどは実物を import せずパラメータで渡す。import 時に時計や環境をバインドするモジュールは、開発者のマシンに触れずにテストできない。それはテストの不便ではなく設計の欠陥である。
- 「挙動を変えないリファクタリングだから」はテストを書かない理由にならない。コードの移動はその中のルールについて何も証明しない — 移動で露出したルールだけでも抽出してテストする。
- 新しいテストが**対象コードが壊れたときに落ちる**ことを必ず確認する。条件を一時的に反転させる・ガードを消す・修正を revert するなどして赤くなるのを見届けてから戻す。壊れたコードでも通るテストは別の何かをテストしている — これは頻繁に起き、確認しない限り見えない。
- モジュールモック（`vi.mock`）よりも、パラメータで渡すフェイク・スタブを優先する。ロジックに到達するためにモジュールモックが必要なら、たいていそのロジックは抽出を求めている。
- **名前を付ける価値のある最小の純粋関数**に分割し、それぞれに専用のテストを書く — 1 ファイルに 1 テストではなく、1 ルールに 1 テスト。4 つの判断を抱えた 40 行の関数は組み合わせでしかテストできないが、名前の付いた 4 つの関数は直接テストでき、各々のエッジケースは自明になる。
- 既存コードにも適用する。大きなファイルに触れるときは、埋もれている純粋なルールを見つけて抽出し、その作業の一部としてテストを書く。「テスタブル」は新しい行だけを縛るルールではなく、コードベースに能動的に回復させる性質である。
- 何を最初にテストするかは**どれだけ静かに壊れるか**でランク付けする。例外を投げる関数はすでに自己申告している。もっともらしい誤った値を返すもの — off-by-one のインデックス、間違った日付、緩すぎるバリデータ — はユーザーが不正データに気づくまで見えない。そちらが先。
- **意図的な非対称性・既知の制限**はテストとして固定し、理由をコメントに書く。わざと挙動が違う 2 つの類似ヘルパー、意図的に一部の型を無視するバリデータ — 記録しなければ次の読み手が「修正」してしまう。
