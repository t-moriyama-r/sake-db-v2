# デバッグ手法

自明でないバグ調査（複数の原因が考えられる症状、複数箇所に再発するバグ、リトライ機構、特定ブランチでのみ再現するバグ、他リポジトリの状態判断）を始める前に読むこと。

## バグファミリーはマトリクスで潰す

ひとつのエラー症状に複数の根本原因がありうる場合（「バグファミリー」）は、症状 × レイヤー × 条件のマトリクスに全ケースを整理し、それぞれを修正・検証する。たまたま再現した 1 ケースだけ直して兄弟ケースを放置しない。マトリクスはドキュメントとしてコミットし、ケースが静かに退行しないようにする。

## 1 箇所のバグは「ルール」への報告として扱う

ある呼び出し箇所で見つかったバグは、その行ではなく「ルール」に対する報告である。修正前に、同じルールが決定されているすべての箇所をコードベース全体からスイープする。症状ではなく**操作**を grep する（パス結合、エンコーディング／エスケープ、日付・タイムゾーン計算、ID 正規化、比較・ソートキー、単位変換、リトライ／タイムアウトポリシー、権限チェック）。

各ヒットを分類する:

- (a) 同じバグ → 修正する
- (b) 同じルールが手書きで正しく実装済み → 共通化の候補
- (c) 意図的に異なる → 理由を記録して残す

そのうえで「**このルールは 1 つの共有関数にできるか？**」を必ず問う。可能なら抽出し、修正を繰り返す代わりに呼び出し側を共通関数に集約する。手書きコピーが 2 つ以上あることは、ヘルパーが最初から必要だった証拠である。

スイープ結果は件数付きで報告する（N 箇所発見 / M 箇所が実際に壊れている / K 箇所は触ってはならない）。修正範囲を広げるか段階的にやるかの判断はユーザーに委ね、勝手に決めない。見た目が同じでも触ってはいけない箇所（内部値との比較・包含チェック等）を「grep に引っかかったから全部正規化」すると、別のバグと交換するだけになる。

## リトライ・自動復旧機構は敵対的にレビューする

リトライ／自動復旧／リプレイ機構を追加するときは、出荷前に典型的な失敗モードを敵対的にレビューする:

- リプレイ時に副作用が二重実行されないか
- 待機中の中断・キャンセルが処理されるか
- エラーマッチが広すぎて誤リトライが発生しないか

## ブランチ限定の決定的再現は環境ではなくコードを疑う

あるブランチ／コミットでのみ決定的に再現するバグ（main では動くが feature ブランチで壊れる等）の原因は、そのブランチが変更したコードパスにある — 環境ではない。キャッシュ削除や `node_modules` 再インストールの仮説を出す前に、差分のコードパスを二分探索し、そのパスを叩く最小スクリプトで実際の失敗を再現すること。

## 他リポジトリの状態判断は fetch してから

他のリポジトリについて「これは実装済みか？この API は存在するか？」を判断する前に、必ず `git fetch` して `origin/<デフォルトブランチ>` に対して読むこと。ローカル作業コピーは数十コミット遅れた古いブランチにいる可能性がある。「grep で見つからない」は「いま見ているコミットにない」であって「未実装」ではない。

## エラー文字列を唯一の証拠にしない

エラー文字列・ステータスラベル・ログ行が唯一の証拠であるうちは、それを額面どおりに受け取らない。まず一次情報（実際の変数、API の返り値、保存されたレコード）を取得する。異なる状態をひとつのメッセージに丸めている場合（例: 権限プロンプトの「無視」を「拒否」と報告する等）、存在しない原因を探し続けることになる。
